## 🔴 阻塞问题（必须修改后进入下一阶段）

### Q1：状态机存在死循环——L3 转人工后无回归路径

**来源**：研发架构师、测试负责人
**涉及模块**：M1 状态机
**描述**：WAITING_FOR_CONFIRM 超时后升级 L3，但 L3 完成后没有回归路径回到 INACTIVE/ACTIVE。用户在一次超时后永久失去继续对话的能力。同时 COMPLETED 也缺少超时回归到 INACTIVE 的路径。
**建议方案**：增加 COMPLETED → INACTIVE 的超时回归（10min 无消息）；增加 L3 解决后的回归机制（如 ESCALATED → RESOLVED → INACTIVE）。

### Q2：L2 确认卡片缺乏幂等性和并发控制

**来源**：研发架构师、测试负责人、产品运营
**涉及模块**：M2 协作漏斗
**描述**：用户在 WAITING_FOR_CONFIRM 状态下，如果重复点击确认按钮，后端可能收到重复操作请求。如果用户在等待期间发新消息，系统无法判断是确认回答还是新请求。L2 交互的 UI 形态完全未定义（弹窗/卡片/文字）。
**建议方案**：确认卡片带 requestId 做去重；WAITING_FOR_CONFIRM 状态下新消息的处理策略定义；确认后 UI 锁定防重复点击；限制连续 L2 次数（连续 2 次后自动升级 L3）。

### Q3：多租户数据隔离架构完全缺失

**来源**：研发架构师、风控合规负责人
**涉及模块**：全模块
**描述**：Chainup 是白标 SaaS 平台，每个商户的数据必须严格隔离。PRD 仅提到"多租户隔离"四个字。向量检索库是全局共享还是按商户隔离？知识库搜索是否可能跨商户泄露数据？评估数据集是共享还是独立？
**建议方案**：强制独立 Schema 或独立数据库实例进行多商户隔离；向量检索库按商户分索引集合；所有数据访问层强制 tenant_id 参数校验；Redis 缓存 Key 必须包含 tenant_id 前缀。

### Q4：响应时间指标定义不一致

**来源**：研发架构师、测试负责人
**涉及模块**：spec.md、M1
**描述**：spec.md 中响应时间指标 3s，而 M1 模块中 PENDING 超时上限 30 秒才转为异步模式。embedding 查询 + 内部 API 调用链在 3s 内完成几乎不可能。缺乏缓存策略设计。
**建议方案**：统一响应时间指标（推荐 P95 5s）；明确缓存层设计（高频 FAQ embedding 预热、API 数据 TTL 缓存）；如 3s 是硬性要求则需引入 Redis 缓存层。

### Q5：终端用户身份核验缺失

**来源**：风控合规负责人
**涉及模块**：M4 问答引擎、安全与合规
**描述**：Agent 可查询用户资产余额、充提记录、KYC 状态等高敏感数据，但 PRD 无任何终端用户身份认证/授权模型定义。API Token 泄露可能导致批量数据查询。越权查询拦截机制缺失。
**建议方案**：增加终端用户认证章节（SSO/API Token/OAuth 2.0）；每个查询请求必须携带 user_id + signature 后端验签；API 调用频率限制（单用户 ≤30 次/分钟）；敏感数据查询全部写入审计日志。

### Q6：KYC 数据合规链路缺失

**来源**：风控合规负责人
**涉及模块**：M4 KYC 场景、M7 审计日志
**描述**：KYC 拒绝原因等敏感个人数据是否存储在对话日志中？GDPR/个保法要求最小化存储。KYC 数据保留期限未定义。独立数据保留 TTL 和自动清洗策略缺失。
**建议方案**：新增 KYC 数据处理专项章节；对话日志中 KYC 相关内容自动脱敏；KYC 数据设置独立保留 TTL（建议 ≤30 天）；删除操作需有完整审计轨迹。

### Q7：灰度与回滚策略完全缺失

**来源**：产品运营负责人、研发架构师
**涉及模块**：M6 评测监控
**描述**：无灰度层级设计（商户灰度/用户比例灰度/场景灰度）、无回滚触发条件与流程、无 AB 对比机制、无静默模式（影子运行）。上线即全量风险极高。
**建议方案**：增加灰度编排章节，定义三阶段灰度（影子模式→有限灰度→全量开放）；定义回滚触发阈值（如连续 10 分钟转人工率 > 50% 自动回退）；灰度期设置对照组。

## 🟡 需确认问题（建议澄清后再进入开发）

### Q8：embedding 基础设施依赖未评估

**来源**：研发架构师
**涉及模块**：M4 问答引擎
**描述**：embedding 模型选型（开源 vs 商业 API）、部署方式（本地 GPU vs API 调用）、向量数据库选型（Pinecone/Milvus/Weaviate/Qdrant）均未定义。embedding 服务不可用则 Agent 全链路瘫痪。
**建议方案**：PRD 增加「基础设施依赖清单」章节。

### Q9：多轮对话上下文管理未定义

**来源**：研发架构师
**涉及模块**：M4 问答引擎
**描述**：单用户会话上下文窗口大小、过期策略（30 分钟不说话是否清空）、跨设备连续性、持久化方案（Redis vs DB）均未定义。
**建议方案**：明确定义会话 TTL、上下文窗口上限、轮数上限及超时归档策略。

### Q10：五因子置信度模型缺乏校准方案

**来源**：研发架构师、风控合规负责人
**涉及模块**：M3 置信度阈值
**描述**："语义匹配度"和"意图清晰度"在 embedding 搜索中高度重叠，正交性存疑。无历史数据时的冷启动策略缺失。50% 阈值边界附近的大量误判风险未评估。风险因子权重模糊，关键词触发应强制 L3 而非加权计算。
**建议方案**：标注数据集做置信度模型离线验证 AUC；明确冷启动策略；高风险关键词触发时跳过置信度，强制 L3。

### Q11：L3 转人工集成方案未定义，存在敏感数据扩散风险

**来源**：研发架构师、风控合规负责人
**涉及模块**：M2 协作漏斗
**描述**：Agent → 人工客服系统的数据传递协议、加密方式、鉴权方式均未定义。对话上下文的敏感数据在传输中可能泄露。无"最小化传递"原则（应只传摘要而非全量原始内容）。
**建议方案**：强制 TLS 1.3 加密传输；默认只传"问题摘要"+ "未解决原因"；全量历史仅按需提供且需鉴权；商户可配置转交数据的详细程度。

### Q12：商户运营负担缺乏评估

**来源**：产品运营负责人
**涉及模块**：M5 商户配置、全局
**描述**：知识库维护每周工时未评估；中小交易所运营团队技术能力是否满足配置要求不确定；Agent 训练 vs 人工培训的技能要求不同。缺少成本测算模型（Token 消耗 vs 人工薪酬 ROI）。
**建议方案**：补充商户运营负担评估章节；提供开箱即用知识库模板；设计智能推荐配置；补充成本测算模型。

### Q13：上线前后运营流程与 SOP 缺失

**来源**：产品运营负责人
**涉及模块**：全局
**描述**：知识库上线审核流程、商户培训计划、上线检查清单、首日护航机制、日/周/月运营看板、定期迭代节奏、退订流程均未定义。
**建议方案**：补充运营 SOP 文档；M5 补充 Agent 效能仪表盘；首批灰度商户 72 小时护航机制。

## 🟢 建议项（当前可接受，建议改进）

### Q14：全局限流保护缺失
**来源**：研发架构师
**描述**：仅"同用户 5s 内相同输入去重"，缺少商户级 QPS 上限、LLM API Token 日预算硬上限。
**建议**：三层限流——商户级 QPS、用户级冷却期、LLM API Token 日预算硬上限。

### Q15：P0 自动停用策略影响体验
**来源**：研发架构师
**描述**：P0 自动停用中断正在进行的会话，用户操作半途而废。
**建议**：改为暂停新请求入队，允许已有会话完成，或自动将进行中会话升级 L3 转人工。

### Q16：数据反馈闭环自动化链路不明确
**来源**：研发架构师
**描述**："人工复核后触发改进"的具体执行路径——是改知识库还是触发模型微调？如何防止改进退回到之前的表现？
**建议**：明确标注数据集版本管理 + A/B 评估流水线。

### Q17：评测数据集覆盖场景未定义
**来源**：研发架构师、测试负责人
**描述**：500+ 条标注的场景分布比例（六大场景各多少？边界情况占比？）未定义。
**建议**：统一指标定义并明确标注数据集场景分布比例。

### Q18：agent 回复合规护栏不完整
**来源**：风控合规负责人
**描述**：何时必须拒绝回答（如"怎么绕过 KYC""如何搬砖套利"）；合规触发后的审计记录；免责声明的统一性。
**建议**：建立硬性拒绝回答场景清单；合规护栏触发次数计入监控告警。
