## 二、问题分类体系（Issue Cause Category）

### 树形结构

```
Product Requirement Issue（产品需求问题）← ~30%
├── Product Optimization（产品优化）← 最常见
├── Customer Custom Requirement（客户定制需求）
├── New Requirement（新需求）
└── Product Not Supported（产品不支持）

bug（缺陷/Bug）← ~25-30%
├── APP（移动端 Flutter）
├── Futures Backend（合约后端）
├── Spot Backend（现货后端）
├── Frontend Web + H5（前端）
├── Dex 后端
└── Others

Not a Bug（非Bug）← ~15-20%
├── Customer Inquiry（客户咨询）← 最常见
├── Customer Doesn't Know How to Use（客户不会用）
├── 正常业务逻辑
├── 无法复现
├── 国际网络环境问题
└── Others

Configuration Issue（配置问题）← ~5-8%
├── Customer Configuration Issue（客户配置问题）
└── Chainup Configuration Issue（Chainup内部配置问题）

Data Issue（数据问题）← ~5-8%
Wallet Deposit/Withdrawal Issue（充提问题）← ~3-5%
Third-Party Issue（第三方问题）← ~3-5%
└── VPN Service / Email Service / SMS Service

Others（其他）← ~5-10%
Project Work Order（项目工单）← ~3-5%
APP相关问题 ← ~2-3%
```

### 分类使用要点

- 分类不清时优先选 **Not a Bug → Customer Inquiry** 而非直接 Others
- Bug 必须选对端（APP/Futures/Spot/Frontend）
- Product Optimization 是默认的 Optimize 类入口

## 五、超期识别与风险信号

### 容易超期的工单特征

| 特征 | 风控等级 | 原因 |
|:----|:--------:|:----|
| P2 + 产品优化类 + ueex | 🟡 中 | 涉及前后端联调，排期长 |
| 多处理人协作（handler > 2人） | 🟡 中 | 协作沟通成本高 |
| Pending Acceptance 滞留 | 🔴 高 | 客户反馈周期慢 |
| Customer Custom Requirement | 🟡 中 | 定制开发周期长 |
| Wallet/充提相关 | 🟡 中 | 涉及资金安全，处理谨慎 |
| 76天未更新（如 #10999336） | 🔴 严重 | 需要紧急安抚客户 |

### 超期预警阈值

- 14 天无更新 → 需关注
- 30 天无更新 → 需推动
- 60 天无更新 → 紧急安抚

## 六、处理模板

### 模板A：纳入迭代排期
```
可以作为优化需求处理。
预计纳入 [XX月/迭代] 的优化工单中。
评估优先级：P[0-4]。
```

### 模板B：合并到聚合工单
```
作为优化需求进行处理，合并到私有化/通用优化工单中。
```

### 模板C：咨询类回复
```
经确认，[结论]。
回复客户：[具体内容]。
如需进一步评估，可以提交产品需求工单。
```

### 模板D：超期安抚
```
确认该需求已在评估中，当前进展：[进展说明]。
预计排期：[时间或计划]。
感谢耐心等待。
```
