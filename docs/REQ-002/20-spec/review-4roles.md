# REQ-002 四角色预审报告

> PRD: Google / Apple 社交登录集成 | 评审日期: 2026-05-20 | 状态: Draft

---

## 🔧 角色一：挑剔的技术负责人

### Q1-1. 账户合并冲突：同一个 Google 账号先后绑定了两个不同的交易所账户 — 无兜底策略
- **问题**：`UNIQUE(provider, provider_account_id)` 只防了同 provider 重复绑定，但一个 Google 账号可以先后绑定到不同的邮箱账户（先绑 A 再解绑再绑 B）。更危险的是，如果用户**同时用邮箱 + Google 创建了两个独立账户**，两个账户都做了 KYC 且产生了交易/充值，后续无法合并，也没有制定由谁合并、何条件下允许合并的策略。
- **建议**：新增 `social_login_conflict` 状态机：`NO_CONFLICT → CONFLICT_DETECTED → USER_MERGE → ADMIN_ESCALATE`。当检测到跨账户绑定同一 social identity 时，触发合并审批流程或拒绝操作。
- **严重度**：🟠 严重

### Q1-2. Apple 中继邮箱变更→用户身份漂移，账号可能丢失
- **问题**：Apple 的隐藏邮箱中继（`xxx@privaterelay.appleid.com`）在同设备上每次登录可能**产生不同的 relay email**（取决于用户是否在 Apple ID 设置中关闭"邮件转发"）。如果用户第一次登录用 relay email A，换设备后用 relay email B，后端依赖 relay email 做匹配会失败，导致创建第二个账户。即使 key 是 `provider_account_id`（sub claim），此 claim 在同一 Apple ID 下是稳定的，但 PRD 未明确保证**依赖 sub 而非 email**。
- **建议**：在 DB schema comment 和代码中明确**主键匹配只依赖 sub (provider_account_id)**，email 仅用于展示和通知。同时 AC-03 应补充「同一 Apple ID 跨设备登录仍归为同一账户」验收。
- **严重度**：🟠 严重

### Q1-3. id_token 有效期 + OAuth 授权码 replay — 缺少 nonce / state 防重放
- **问题**：PRD 只提了 id_token 后端验证，但未提 **nonce** 或 **state** 参数。Google 和 Apple 的 id_token 一旦在传输中被截获（MITM），攻击者可以直接 replay 到 POST endpoint 登录任意账户（如果该 Google 账号已绑定）。Apple 文档明确要求含 state 参数防 CSRF。同样，Google 推荐 nonce 验证。
- **建议**：前端每次发起 OAuth 时生成一次性的 `nonce` + `state`，后端在验证 id_token 时校验 nonce 是否匹配。把这写到 NFR 安全条款里。
- **严重度**：🔴 致命

### Q1-4. 地区限制基于 IP 检测—IP 变更导致登录态闪退风险
- **问题**：地区限制在**登录页加载时**检测 IP，但如果用户已登录、在登录后 IP 变更（VPN 切换、漫游），社交登录按钮不会重新检测。更严重的是，如果某用户从允许地区登录后，IP 变更为受限地区，此时「安全设置」页的绑定/解绑操作是否也受限？PRD 未定义地区限制的**作用域（仅登录页 vs 全局）**。
- **建议**：明确定义地区限制检查的 scope。账户层面的社交绑定/解绑操作是否也应受 IP 限制？建议强制解绑操作也走 IP 检查，避免受限地区用户通过 VPN 注册后解绑合规账户来规避限制。
- **严重度**：🟡 中等

### Q1-5. 状态机缺漏：OAuth 中间态无超时/清理机制
- **问题**：用户点击 Google 登录 → 弹出 OAuth 授权页 → 用户**不确认不取消，直接关掉窗口**。此时前端按钮状态未恢复（loading 态卡死），后端也没有超时清理机制。另外，如果用户 OAuth 授权成功但后端 id_token 验证超时（>500ms），用户看到的是空白页重定向还是错误？
- **建议**：前端增加 30s 超时重置按钮状态，后端 social 端点增加请求级超时和幂等 Token 防重复提交。
- **严重度**：🟡 中等

### Q1-6. Apple 私钥轮转与密钥管理 — 无密钥失效/刷新流程
- **问题**：Apple Sign-In 需要服务端使用**私钥（.p8 文件）+ Key ID + Team ID** 来生成 client_secret。该私钥如果泄露，攻击者可伪造 Apple id_token。PRD 未提及密钥的存储方案（KMS / Vault）、轮转周期、以及密钥失效后的错误处理和监控告警。
- **建议**：明确 Apple 私钥存放于密钥管理服务（AWS KMS / HashiCorp Vault），设置 90 天自动轮转，新密钥发布时有至少 24h 重叠窗口避免断服。增加 `apple_key_expiring_soon` 指标告警。
- **严重度**：🟠 严重

## 🧪 角色二：QA 测试 Lead

### Q2-1. 同邮箱同时存在邮箱账户 + 社交账户的重复账户无检测
- **问题**：Alice 先用邮箱 `alice@gmail.com` 注册了交易所账号，后来用 Google 登录（Google account email 也是 `alice@gmail.com`）。后端此时有两个独立的账号，email 相同但 provider 不同。PRD 的护栏指标「重复账户比例 ≤ 1%」只监测了结果，完全没有检测手段。这两个账号后续在主站中谁能做 KYC、谁有资金、能否合并？完全未定义。
- **建议**：在 `POST /api/v1/auth/social/google` 中增加**邮箱碰撞检测**：如果 Google 返回的 email 已存在于 `users` 表，则提示「该邮箱已注册，是否绑定到现有账户？」提供合并/绑定引导流程。
- **严重度**：🔴 致命

### Q2-2. 跨功能交叉场景：社交登录 + 2FA + 反钓鱼码
- **问题**：用户 Carol 已绑定 Google 登录，且开了 2FA（TOTP / SMS）。如果用 Google 一键登录，**是否还需要 2FA**？PRD 只说了「直接登录成功」，但没区分「是否跳过 2FA」。如果跳过，安全降级；如果不跳过，一键登录的价值大打折扣。同样，如果用户设了反钓鱼码（anti-phishing code），社交登录登录后的首页是否需要展示该码？
- **建议**：明确以下规则：社交登录**首次设备/新设备检测后仍需 2FA**（同现有"信任设备"逻辑）；已信任设备可跳过 2FA。反钓鱼码始终展示，与登录方式无关。
- **严重度**：🟠 严重

### Q2-3. 解绑后重新绑定同一 Google 账号 — 状态清理不完整
- **问题**：用户解绑 Google 后，`user_social_accounts` 记录被删（或标记删除？PRD 未说）。如果用户再次绑定同一个 Google 账号，是否正常走？如果记录被软删除（逻辑删除），unique key 约束会阻止重新插入。
- **建议**：明确解绑是硬删除还是软删除（`deleted_at`）。如果是软删除，unique key 需要包含 `deleted_at IS NULL` 的条件唯一索引（或使用 NULL 软删除技巧）。增加 AC 测试用例：解绑 → 重新绑定 → 验证成功。
- **严重度**：🟡 中等

### Q2-4. 网络状况异常：OAuth 完成但后端 id_token 验证请求超时
- **问题**：用户已在 Google 授权页点了「允许」，浏览器拿到了 authorization code 并发送到后端。但后端在请求 Google token endpoint 时网络抖动超时（超过 500ms）。前端收不到响应，用户看到的是白屏或"登录失败"。此时 Google 端 authorization code 已消耗，无法重试。
- **建议**：前端增加**轮询/等待机制**（最多等 10s），后端实现**异步幂等处理**：首次请求生成 `request_id`，超时后前端用同一 request_id 轮询结果，后端缓存处理结果 2 分钟。
- **严重度**：🟡 中等

### Q2-5. 测试数据隔离与 mock 策略缺失
- **问题**：Google 和 Apple 的 OAuth 测试需要在 Sandbox 环境下用真实 Apple ID / Google 账号，且 Apple Sign-In 的 Sandbox 需要**特定的测试 iCloud 账号**（非生产账号），配置复杂。PRD 完全没有提及测试账号准备、Mock 策略、或者 CI 中如何 mock OAuth 响应。
- **建议**：为 QA 提供测试方案文档：(1) 准备专门的测试 Google 账号 / Apple Sandbox 测试账号清单；(2) 提供 WireMock / MSW mock 方案，使 CI 能跑单元测试；(3) 明确 staging 环境的 OAuth redirect URI 与 prod 不同，避免串数据。
- **严重度**：🟡 中等

### Q2-6. 并发解绑 / 重复绑定 — 缺少悲观锁/乐观锁
- **问题**：用户同时在两个设备上操作解绑（Web + App），可能触发两次解绑请求，导致 `user_social_accounts` 记录被删两次，或者解绑计数判断出 bug（两个请求都发现还剩一种登录方式，都允许解绑，结果全解光了）。
- **建议**：解绑接口使用数据库行级锁（`SELECT ... FOR UPDATE`）或乐观锁（version 字段），确保并发安全。增加并发解绑测试用例。
- **严重度**：🟡 中等

## 🛡️ 角色三：合规/风控官

### Q3-1. Google / Apple 社交登录完全绕过了密码验证⇒账户接管风险剧增
- **问题**：社交登录本质上是**用第三方身份替代密码**。如果用户的 Google 账号被盗，攻击者可以直接登录交易所。现有「修改密码邮件通知」的机制不再适用（因为用户没有密码可改）。PRD 完全未讨论此场景下的**账户保护机制**，也未要求社交登录用户绑定手机号/邮箱作为备用恢复方式。
- **建议**：强制社交登录注册用户在首次登录后完成**手机号绑定**（用于安全通知和账户恢复）。当社交账号状态变更（Google 密码修改、登录设备变化）时，同步通知交易所原绑定手机/邮箱。
- **严重度**：🔴 致命

### Q3-2. 社交登录暴力枚举 / 批量注册 — 防刷策略仅说"同现有策略"，但现有策略可能不适用
- **问题**：现有邮箱注册防刷靠的是**验证码+IP 频率限制**。社交登录跳过验证码，攻击者可以用大量 Google 账号（或购买的 Google 账号池）批量注册。Google 的 id_token 验证只检查签名有效性，不检查账号「真实性」（一个真人 vs 脚本批量创建）。PRD 的风控触点写的是"同现有策略"，但现有策略的关键防线（验证码）已经被跳过了。
- **建议**：社交登录注册必须叠加额外防刷层：(1) 同一 IP 的社交注册频率限制（比如每小时 N 次）；(2) 社交注册的设备指纹（fingerprint）；(3) Google 账号创建时间小于 24h 的标记为高风险（需额外验证）；(4) 社交注册的 KYC 门槛不得低于邮箱注册。
- **严重度**：🔴 致命

### Q3-3. 法务依赖未定即开展开发 — 地区限制名单可能随监管变化
- **问题**：PRD 写了"需法务确认哪些国家限制使用"，但这是一个**阻塞性依赖**。如果法务确认要 3 周，而开发已经开始，商户后台的「地区限制管理」前端可能按白名单/黑名单做了，但法务最终要求的可能是**按细分监管要求分级别限制**（某些国家只能用 Apple 不能用 Google、某些国家两者都不能用但要显示提示而非隐藏、某些国家有欧盟 GDPR 数据出境限制）。
- **建议**：商户后台的「地区限制配置」设计为**灵活的策略引擎**（策略组 + 策略规则），而非简单的 白名单/黑名单二元切换。预期以下字段：国家代码、允许的 provider 列表、按钮显示模式（隐藏/禁用+提示/完全不可见）、提示文案 key。法务确认结果前，产品需先提供多场景约束模版。
- **严重度**：🟠 严重

### Q3-4. Apple 中继邮箱导致 KYC 邮件验证失效 / 设备绑定校验问题
- **问题**：Apple 隐藏邮箱模式下，用户 KYC 时如果用该中继邮箱接收验证邮件，Apple 的中继服务可能阻隔或延迟重要通知。另外，部分国家（如韩国）的 KYC 要求**邮箱与身份证件上的姓名一致**，中继邮箱（`random@privaterelay.appleid.com`）无法匹配身份证件。可能导致 KYC 无法通过。
- **建议**：强制 Apple 登录用户在 KYC 前补充一个**真实邮箱地址**（或手机号），而不是依赖 Apple 中继邮箱。在后端标记 `is_relay_email = true` 字段，对这些用户延迟或跳过邮箱验证，换用手机验证。
- **严重度**：🟠 严重

### Q3-5. 数据出境的隐私合规 — Google/Apple 用户数据传输至中国/香港服务器
- **问题**：交易所服务器大概率设在中国香港或大陆。Google / Apple 登录涉及将用户的 Google / Apple identity token 发送到交易所服务器，服务器再请求 Google/Apple token endpoint 做验证。这涉及**用户个人数据（email、姓名）跨境传输**。如果服务器在香港、用户在欧洲（GDPR），或服务器在大陆、用户在美国，都需要不同的隐私合规处理。
- **建议**：法务确认的同时，技术侧在用户协议中明确列出第三方数据分享场景（Google/Apple 获取了什么信息、什么信息被发送到了哪个服务器），并在 GDPR 地区用户首次社交登录时弹出**明确的同意收集弹窗**，而非跳过后台直接创建账号。
- **严重度**：🟠 严重

### Q3-6. 商户后台配置归属风险 — 无操作审计日志
- **问题**：商户后台的「地区限制配置」和「全局开关」将直接影响用户能否访问和注册。如果商户运营误操作关闭了某个国家的社交登录（或误打开了一个高风险国家），没有**操作审计日志**（谁、什么时间、改了哪个国家的配置、从什么值改成什么值），出了合规问题无法追溯。
- **建议**：所有商户后台的社交登录配置更改必须有**完整的 Audit Trail**（存入专门的 `admin_audit_log` 表），并由二级管理员审批高风险操作（如放开制裁国家列表）。
- **严重度**：🟡 中等

## 👤 角色四：有经验的交易所客户

### Q4-1. 社交登录注册后无法设置密码 — 账户恢复路径缺失
- **问题**：我用 Google 登录注册了交易所账户，从此没有密码。如果某天我的 Google 账号被封了（或被我手滑删除），我**没有任何方式登录交易所**。没有备用恢复码、没有密码重置流程（因为没有密码），客服工单即使提交也需要验证身份，而我没有 Google 账号就无法验证。这等于把交易所账户的生死权完全交给了 Google/Apple——它们封我，我就丢资产。
- **建议**：社交登录用户在注册后**强制引导设置邮箱密码**（可选跳过但登录页必须提供"设置密码"入口），或提供**10 个一次性恢复码**（类似 GitHub 的 recovery codes），或强制绑定手机号作为第二恢复通道。
- **严重度**：🔴 致命

### Q4-2. 解绑规则不透明 — "至少保留一种登录方式"可能被滥用来锁定用户
- **问题**：PRD 说解绑需至少留一种登录方式。但如果我是用 Google 注册的，唯一的登录方式被我手滑解绑了（比如我在安全设置页点了"解绑"，然后系统说"还有邮箱登录方式"，但我的邮箱验证码发到了我无法访问的邮箱），我就被锁在外面了。另外，如果系统 bug 导致解绑后记录仍存在但失去了关联，我既不能邮箱登录（因为邮箱账号不存在）也不能 Google 登录（因为系统认为已绑定但实际解绑了）。
- **建议**：(1) 解绑前二次确认弹窗明确提示 "解绑后你将无法使用 {Google} 登录此账户，当前剩余登录方式: {邮箱}/ {手机}。确认解绑？"；(2) 增加24小时解绑冷静期，解绑后 24h 内可撤销；(3) 记录解绑操作的可恢复性（软删除）。
- **严重度**：🟠 严重

### Q4-3. 地区限制缺乏透明度 — 被"静默隐藏"且无申诉渠道
- **问题**：Dave 在受限国家，看到登录页的社交登录按钮被隐藏了，没有解释原因。Dave 可能以为自己浏览器有问题、或者交易所歧视他的国家。如果 Dave 实际上是通过合规 VPN 在合法地区工作，被 IP 数据库误判（误拦截率 0.1% 意味着每 1000 个用户就会有一个被误伤），而且**没有任何申诉/重新检测的入口**。
- **建议**：(1) 按钮隐藏时增加 提示文案：`"您所在地区暂不支持此登录方式。如有疑问，请联系客服。"` (支持多语言)；(2) 提供一个 **"重新检测"** 按钮（手动刷新 IP 检测）；(3) 建立误拦截申诉工单流程，客服可手动覆盖地区限制标签。
- **严重度**：🟡 中等

### Q4-4. Apple 隐藏邮箱导致通知收不到 — 资产变动无感知
- **问题**：我用 Apple 隐藏邮箱注册了交易所，交易所发来的重要通知（提现验证码、API 密钥变更、登录新设备通知）都发到了 `xxx@privaterelay.appleid.com`。Apple 的邮件中继有时会延迟甚至丢弃邮件（尤其是批量通知）。我可能错过了资产安全通知。
- **建议**：(1) 强制 Apple 登录用户在首次登录后绑定手机号，所有安全通知以 SMS 为主；(2) 在 App 内增加「安全通知中心」，所有重要通知通过 App Push + 站内信双通道送达；(3) 用户协议中明确说明中继邮箱可能产生延迟/丢失，建议补充手机号。
- **严重度**：🟡 中等

### Q4-5. 隐私担忧：为什么交易所需要我的 Google 邮箱和真实姓名？
- **问题**：Google OAuth 首次授权时会展示权限范围（`email`、`profile`）。用户会看到 "此应用将获取你的姓名、邮箱地址、个人资料图片"。在交易所场景下，用户可能会担心："为什么一个交易平台需要我的真实姓名和头像？" 如果用户拒绝授予某权限，登录流程会失败，但用户不知道失败原因。
- **建议**：(1) OAuth 请求前展示清晰的权限说明弹窗："我们将获取你的 {Google 账号邮箱} 用于创建账户，不会获取你的通讯录或发布内容到你的账号。"；(2) 将 OAuth scope 最小化（只请求 `email` 和 `openid`，不请求 `profile` 以避免获取姓名头像）；(3) 如果用户取消授权，展示友好文案引导用户使用邮箱注册替代方案。
- **严重度**：🟢 次要

### Q4-6. 同一人同时有社交账户和邮箱账户 — 资产隔离不透明
- **问题**：我不小心用 Google 登录创建了一个新账户（登出状态下点了 Google 登录），而之前我已经有一个邮箱账户了。我现在有两个账户，里面可能都有资产。交易所没有任何弹窗提醒我 "此邮箱已有账户，是否合并？" 如果我把钱转到社交账户后忘记了，就是一笔永久沉默资产。
- **建议**：首次社交登录成功但检测到邮箱冲突（Google email 已在 users 表存在）时，弹出合并引导流程，允许用户选择「关联到现有账户」或「创建新账户」，并明确告知「不合并可能导致资产分散在两个账户中」。
- **严重度**：🟡 中等
